日期：2026-10-13。范围：到期生成、通知入队、渠道独立、重复扫描及失败处理。结论：本机自动联调通过，**W6-D6 部分完成**，指定邮箱和飞书测试群的真实收件尚待配置与验收。

## 已入队通知的恢复缺陷

原后台只选择 `RETRY`，成功任务入队为 `PENDING` 后、首次发送前进程退出，记录会一直保留但没有扫描者领取。隔离 MySQL 用例 `notificationsQueuedBeforeAnInterruptionRemainDispatchable` 在修改前失败：期望邮件 / 飞书两条可领取，实际为空；单用例 1 项失败、0 错误，确认不是环境故障。

最小修复将查询改为尚未首发的 `PENDING` 或已到期的 `RETRY`，只选仍启用的渠道且次数小于 3，按待发送时间 / 创建时间和 ID 取前 100 条。继续复用发送前的数据库原子领取；已发送、结果未知、发送中和明确失败均不自动重发。关闭的渠道保留记录但不参与这 100 条选择，避免占满批次阻塞其他用户；重新启用后旧待投递记录可能继续发送。方法改名为 `dueDeliveries`，不改变接口 DTO 或数据库迁移。

恢复测试还验证：两渠道关闭时不领取，重新开启后扫描派发到两个发送器；成功与 UNKNOWN 不再进入扫描，不能再次领取。原飞书退避用例针对飞书渠道断言，避免将另一个尚未首发的邮件记录误当作提前重试。

进一步故障注入确认第二个缺口：任务先标为成功，再入队，入队失败没有可恢复的任务状态。修改前单用例失败，期望 RUNNING、实际 SUCCEEDED。现将触发完成状态与两渠道入队放在一个短数据库事务内，模型调用和外部发送均在事务外；入队异常回滚这部分写入，已经生成的整周结果保留。恢复流程同样以事务记录结果和入队，失败后保留 RUNNING 供下次核对，不重新调用已成功的模型阶段。此改动保护新的完成与恢复写入，不主动给历史 SUCCEEDED 任务批量补发。

## 自动生成到通知联调

`ScheduledNotificationIntegrationTest` 使用隔离 MySQL / Redis、实际 GenerationJobScanner / GenerationService / LangGraph4j / ModelGateway、已有本地 OpenAI 兼容 HTTP 替身。测试用固定时间直接驱动生产扫描方法，自动墙钟扫描保持关闭。邮件 / 飞书发送器使用测试替身，因此验证到派发边界，不证明实际 SMTP 或飞书送达。

| 演练 | 观察结果 |
| --- | --- |
| 到期前 / 到期后 | 到期前无触发；到期后一个 SCHEDULED 运行成功，保存 2 条 Java / 1 条英语草稿 |
| 同周期再次扫描 | 仍一个触发、六次 HTTP 模型调用及六条账本，发送器无额外交互 |
| 邮件派发异常 | 两条渠道记录均已入队；邮件派发抛异常后飞书仍被派发 |
| 已确认内容 | 独立已有确认稿的内容、来源、状态和版本保持不变 |
| 上游失败 | 本地 HTTP 模型返回 503，运行失败于 slot1/generateDraft，无整周结果和成功通知；重复扫描不再调用 |
| 预算拒绝传播 | 在真实 UsageLedger 的 spy 接缝注入 BudgetPaused，网关停止于 USER_CALL_LIMIT_REACHED，零 HTTP 模型调用、无通知 |
| 入队及恢复中断 | 首次完成和第一次恢复都在插入通知后注入异常，均回滚状态 / 两渠道记录；再次恢复入队两条，后续核对不重复，模型仍为六次 |

预算这一项验证拒绝传播，不替代 W5 对真实额度计算和并发预留的验证。测试结束关闭本例任务和通知渠道，避免留下可自动执行的样例配置。
