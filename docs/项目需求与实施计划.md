# 抖音内容创作与运营 Agent：需求与实施计划

整理日期：2026-09-24。本文记录需求访谈中已确认的范围、约束和排期，作为后续开发依据；不表示功能已经实现。

每日执行清单见：[8 周每日开发任务](superpowers/plans/2026-09-24-agent-daily-development-plan.md)，包含 56 天的任务、每日用时、涉及文件及完成标准。

## 1. 项目目标

开发一个前后端分离的个人内容创作与运营 Agent，支持多用户独立使用，每个用户可以管理一个或多个抖音账号。

第一阶段优先完成资料检索、选题、脚本、内容排期的创作闭环。发布作品并取得真实数据后，再通过数据导入或可用接口进行运营复盘。抖音数据接入不作为 Agent 开发的前置条件。

同行账号作为补充研究对象，可使用实际可获取的公开信息或用户提供的材料。第一版不承诺自动获取任意同行账号的完整指标。

## 2. 已确认的首个使用场景

当前抖音账号尚未注册，没有历史作品和运营数据。先用一个账号验证产品，同时保留多用户、多账号的系统设计。

| 项目 | 已确认内容 |
| --- | --- |
| 主要栏目 | Java 面试八股文快问快答 |
| 辅助栏目 | 为托福考试准备的英语口语跟读记录 |
| 初始主要受众 | 程序员；英语栏目以个人备考记录为定位 |
| 制作形式 | 录屏、口播；用户自行录制和剪辑 |
| 每周频率 | 3 条：2 条 Java + 1 条英语 |
| 英语素材方向 | 名人演讲段落、托福相关学习资料、《科学美国人》60 秒等 |
| 英语支持范围 | 选材、材料整理、断句、解释、练习提纲、视频文案和排期 |

不将英语内容强行限定为程序员英语。第一版不包含录音上传评测、发音打分或官方托福评分预测。

账号定位、栏目比例和更新频率应可修改，不写死在业务代码中。生活类账号是此前讨论过的方向，不是当前首个账号的验证场景。

## 3. 已确认的业务能力

### 3.1 用户与账号

- 邀请注册，先面向本人和少量受邀测试用户。
- 每个用户独立管理自己的多个内容账号，不引入团队共享、成员邀请协作和团队角色体系。
- 抖音账号注册和授权前，可以先建立内部内容账号配置，用于内容策划。
- 用户的数据、上传资料、对话、报告、任务、通知配置和第三方授权相互隔离。
- 数据库、缓存、工具调用、检索、异步任务均须执行用户归属校验；仅隔离对话 memoryId 不足以满足要求。

### 3.2 素材与资料

- 用户提供资料或链接，Agent 优先使用用户资料，需要补充或核实时再联网检索。
- 检索和生成结果保留可核对的来源。无法取得依据时明确说明，不编造引用或链接。
- 个人上传资料仅供所属用户访问，不自动向其他用户开放。
- 对 Java 内容提供技术依据，涉及版本差异时注明版本。
- 私人练习素材与可用于公开发布的素材需要区分；不将能访问某份材料视为可全文转载。

### 3.3 选题、脚本与排期

三类交付物均属于第一版范围：

1. 选题卡片：标题、目标受众、内容角度、推荐依据、开头钩子、简单拍摄提纲。
2. 可拍摄脚本：完整口播文案、必要的代码或演示步骤、分镜或录屏建议。
3. 内容排期：按每周更新目标组织选题和脚本，在站内内容日历查看和修改。

用户可以单独执行某一步，也可以要求一次生成整周方案。Java 快问快答可采用“问题—简洁回答—关键解释或示例—常见追问”的组织方式。

排期表示内容计划，不包含自动发布抖音。推荐质量应通过用户审阅和后续真实发布结果验证，不承诺播放量或爆款。

### 3.4 对话与定时运行

- 对话驱动：按需查资料、调用工具、分析内容、生成结果，并支持追问修改。
- 定时驱动：按配置自动生成分析结果、选题、脚本和排期草稿。
- 对话时既支持逐步确认，也支持直接生成整周草稿。
- 定时任务的生成结果等待用户审阅；内容至少区分待审阅和已确认。
- 自动任务不得覆盖用户已修改或已确认的内容。
- 两种入口复用分析和生成能力；数据同步与模型分析分开运行。
- 生成报告注明数据来源和更新时间；新号不能生成冒充真实表现的趋势分析。

### 3.5 Tool 与 MCP

- 第一版包含本地 Tool 和 MCP Client。
- 本地 Tool 负责资料检索、账号配置查询、历史内容查询、指标计算、保存草稿和排期等业务操作。
- MCP Client 优先接入联网搜索，具体服务商和接入方式需实施时验证。
- 第一版不建设 MCP Server。
- 模型不能决定用户身份或授权范围。工具执行前由后端校验身份、资源归属和参数。
- 第三方工具仅获得完成请求所需的信息，不因接入 MCP 而自动获得整个用户资料库的访问权限。

### 3.6 通知

- 支持邮件与飞书机器人，每个用户可独立配置、选择一个或同时开启。
- 任务结果保存在站内，外部通知发送简短摘要和访问链接。
- 打开链接仍需登录并校验结果归属。
- 一个通知渠道失败，不影响报告保存或另一个渠道发送。
- 通知频率、合并规则和重试参数在实现时确定。

### 3.7 数据监控与复盘

- 目标指标包括作品播放量、点赞量、评论数，以及在数据源允许时取得的评论正文。
- 第一版支持使用真实导入数据完成复盘；官方自动同步根据应用资质、用户授权和接口权限接入。
- 自有账号不等于无需申请接口权限。自动监控须在持续更新的数据源接通后单独验收。
- 同行资料和可用指标可作为辅助输入；不假设能取得同行播放量、完播率或完整评论。
- 缺失数据明确标记，不填成零，不由模型推测后冒充事实。
- 演示数据只用于开发验证，须与真实账号数据区分。

## 4. 技术与部署约束

| 项目 | 已确认约束 |
| --- | --- |
| 架构 | 前后端分离 |
| 前端 | Vue 3 + TypeScript |
| 后端 | Java + Spring Boot 3 |
| AI 框架范围 | LangChain4j / LangGraph4j；具体组合在技术方案中确定 |
| 数据库 | MySQL |
| 缓存及 Java 客户端 | Redis + Redisson |
| 模型 | 云端 DeepSeek API |
| 模型凭据 | 统一使用项目方的 API Key，仅由后端管理 |
| 成本管理 | 按用户记录用量、限制额度，共享系统预算 |
| 外部调用预算 | 全部用户合计暂定 100 元/月，不含已有服务器费用 |
| 服务器 | 腾讯云，4 核 CPU、4GB 内存、40GB 系统盘 |
| 现有环境 | 宝塔 Linux 面板；发行版、版本、地域与现有服务占用尚未确认 |

100 元是预算目标，不是已验证的费用预测。应用侧用量估算需要与供应商账单核对，不承诺在缺少实时计费数据时做到绝对精确的金额封顶。

部署建议采用单机 Docker Compose，Vue 构建产物通过 Nginx 提供访问；实施前检查宝塔现有网站、端口、数据库和内存占用，确定复用或新增组件的方式。不得以重装服务器作为默认前提。

初版限制任务并发并配置日志轮转。服务器主要保存指标、文本、报告和脚本，不默认保存视频原文件。实际容量需要通过观测和测试确认。

## 5. 三个里程碑与八周排期

投入约束：一人开发、AI 辅助，每周 15 小时。目标 8 周，共约 120 小时；第 9 周作为联调或部署缓冲。尚未约定具体开工日期，不将周次转换为已承诺的日历日期。

| 周次 | 主要工作 | 可验证结果 |
| --- | --- | --- |
| 第 1 周 | 工程骨架、登录、用户隔离基础；DeepSeek、本地 Tool、一个 MCP 搜索服务的最小接入 | 登录后完成真实工具调用，验证框架和模型的兼容性 |
| 第 2 周 | 账号配置、资料导入与检索、来源记录 | 可查询本人资料，不能检索其他用户资料 |
| 第 3 周 | 对话式选题、Java 脚本、英语材料整理、拍摄提纲 | 根据资料生成内容，并通过追问修改 |
| 第 4 周 | 周排期、草稿编辑和确认、完整流程联调 | 里程碑①：生成并审阅 2 条 Java + 1 条英语内容，可开始实际使用 |
| 第 5 周 | 定时执行、失败处理、重复执行控制、模型用量和额度 | 自动生成草稿，不覆盖已确认内容，用量可追踪 |
| 第 6 周 | 邮件、飞书、通知与审阅流程联调 | 里程碑②：定时生成、通知、登录审阅完整可用 |
| 第 7 周 | 真实作品数据导入、趋势展示、运营复盘 | 根据真实输入生成报告，明确缺失指标 |
| 第 8 周 | 腾讯云部署、资源配置、HTTPS、备份恢复、验收 | 里程碑③：线上版本可用，基本运行与恢复验证通过 |

前期估算范围：里程碑①约 45～60 小时，②约 20～30 小时，③约 25～45 小时，总计约 90～135 小时。第 1 周接入验证后、第 4 周完整验收后分别重新估算剩余工作。

估算不包含抖音官方审核等待时间，也不默认包含扫描件 OCR、音视频转写、自动剪辑或录音评测。官方接口不具备条件时，以真实数据导入完成运营复盘验收，并明确尚未实现自动监控。

## 6. 验收建议

以下是将已确认需求转成测试场景的建议，实施时细化为可执行检查。

- 冷启动：未绑定抖音的新账号，能基于账号配置和资料完成一周三条内容；不虚构历史表现。
- 资料与来源：能够指出生成内容的依据，来源不可用时明确提示，搜索失败不冒充成功。
- 工具调用：完成真实本地 Tool 与 MCP 工具调用；失败时给出可理解的状态，不靠固定示例假装执行成功。
- 用户隔离：用户甲无法通过页面、接口、搜索、对话、工具参数或后台任务访问用户乙的资源。
- 人工修改：对话修改及定时重新运行不会静默覆盖已修改、已确认的草稿。
- 定时任务：重复触发不会产生重复的同一批内容或失控的重复付费调用；失败状态可查询。
- 通知：邮件与飞书分别可用；单渠道失败时结果仍在站内可见。
- 复盘：输入真实作品数据后，计算结果可核对；模型解释区分事实与假设。
- 部署：服务重启后业务数据可用；完成一次备份恢复验证，检查实际资源占用。

## 7. 开发前及接入时需要验证的事项

这些事项当前未被用户确定，不应当作已经完成的配置或新增的阻塞性审批。

1. DeepSeek 的实际服务入口、可用模型、框架版本兼容性。密钥通过部署配置提供，不写入文档或前端。
2. MCP 搜索服务的供应商、凭据、费用、网络可达性和工具返回格式。
3. 首版资料导入格式、大小限制与检索实现。暂不假定必须部署额外向量数据库。
4. 真实指标导入模板、时间粒度、数据来源；官方账号授权能力另行验证。
5. 定时生成的具体时间、时区、通知策略及内容日历的默认发布日期。
6. 邮件发送服务及飞书机器人配置，凭据由各自配置途径安全提供。
7. 服务器发行版、现有资源占用、域名和 HTTPS 条件，以及适用的公开访问要求。

技术建议：评估 LangChain4j 负责模型与工具接入、LangGraph4j 负责有状态流程的组合。先用最小端到端原型验证，不因框架名称而拆出不必要的服务或多 Agent。
